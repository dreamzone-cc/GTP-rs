## المرحلة 2 — تمثيل ECN (نصف يوم إلى يوم، قرار نطاق)

المشكلة: `ecn=0` دائماً → خط ECN كامل ميت (عدّادات → `on_ecn` → تفاعل ازدحام).

مساران:
- **أ (موصى به)**: استقبال CE فعلي عبر `socket2` recvmsg مع cmsg (IP_TOS / IPV6_TCLASS)، استخراج حقل الـ2-بت، تطبيعه بترميز AckTracker (1=ECT1، 2=ECT0، 3=CE)، وتمريره عبر `RecvDatagram.ecn` ومسار endpoint (tokio) أيضاً. وسم الإرسال ECT(0) اختياري خلف `GtpConfig`.
- **ب (حد أدنى)**: توثيق ECN كغير منفّذ وإزالة العدّادات الميتة من التقرير — ساعة واحدة.

القبول (مسار أ): اختبار وحدة لتحويل cmsg→ecn + اختبار تكاملي يحقن CE فيcoe tracker ويشهد `on_ecn`.

## المرحلة 3 — مصادقة الخادم وإغلاق فجوة MITM (1–2 يوم، **البند الأعلى قيمة**)

المكونات جاهزة من إصلاحات التدقيق: `HandshakeTranscript` + `compute/verify_server_proof` (بملصق مميز) + توثيق الحدود. المطلوب توصيلها بالسلك بأمان توافق صريح.

### 3.1 تعديل المواصفة أولاً (نصف يوم)
ملحق على `GTP_1_1_Comprehensive_Technical_Specification.md`:
- إطار جديد `ServerFinish { server_proof: [u8; 32] }` بنوع 0x0E ضمن حزمة طويلة الترويسة.
- تدفق جديد: ClientHello → ServerHello → HandshakeFinish → **ServerFinish** → بيانات.
- **ربط رقم النسخة في النص**: حقل `version` موجود في ClientHello — يُضاف للـtranscript ويُردّده ServerHello؛ أي عبث يُكشف بالبرهان.
- سياسة التوافق: النسخة 2 ترفض النظراء النسخة 1 صراحةً بخطأ مصنّف (لا صمت).

### 3.2 التنفيذ (نصف يوم)
- wire: ترميز/فك `ServerFinish` (متماثل مع HandshakeFinish).
- crypto: إدخال `version` في `HandshakeTranscript` (تمديد ميدان واحد).
- endpoint (خادم): بعد التحقق من HandshakeFinish وقبل التسجيل: بناء البرهان وإرسال ServerFinish (وإعادة إرساله مع ACK-policy إذا تكرر Finish).
- endpoint (عميل): مرحلة تأكيد التأسيس الحالية (ping/ACK) تُسبق بانتظار ServerFine والتحقق منه؛ فشل التحقق = `HandshakeFailed("server proof mismatch")` + إغلاق. لا "Established" قبل ذلك.

### 3.3 الاختبارات (نصف يوم)
- e2e نظيف محدّث (handshake_e2e_test).
- **اختبار MITM حتمي**: مهاجم يُكمل ساقين بمادتين → برهان الخادم لا يتحقق عند العميل.
- اختبار تخفيض النسخة: تلاعب بـversion في العبور → فشل.

**بوابة إضافية**: إعادة مسح `ocr scan crates/gtp-wire,crates/gtp-crypto,crates/gtp-runtime-tokio` (تسلسلياً عبر البوابة أو مفوَّضاً) كتحقق مستقل على الشيفرة الجديدة.

## المرحلة 4 — بنود الأداء المؤجلة (نصف يوم، بعد المرحلة 1، مستقلة عن 3)

1. **LRU O(1) للمجموعات المرتبة** (`gtp-core/state.rs:410`): عدّادات جيل رتيبة + مؤشر عكسي صغير للإقصاء الكسول بدل مسح VecDeque لكل إطار مستقبل. قياس قبل/بعد بـ`criterion` على مسار استقبال مشبع (256 مجموعة).
2. **نبض TX تكيفي** (`endpoint.rs:712`): تراجع الفاصل (500µs → حتى 10ms) عند خمول متتالٍ، واستئناف فوري عبر `tokio::sync::Notify` عند كل `send_*`.
3. (اختياري) دمج ثوابت أحجام الداتاغرام إن لم يُنفذ في 1.6.
